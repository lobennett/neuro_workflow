The bidsify code correctly handles subject aliases via timestamp-based session ordering. Example for s29:

```
Flywheel s29:  ses1 (Nov 13), ses2 (Nov 14), ses3 (Dec 2), ...
Flywheel s29-2: ses (Mar 5)  <- collected under wrong label
       ↓
BIDS s29: ses-01 (Nov 13), ses-02 (Nov 14), ses-03 (Dec 2), ses-04 (Dec 4),
          ses-05 (Feb 3), ses-06 (Mar 5) ← s29-2 merged by timestamp
```

## Why Two-Run Approach Was Necessary

The discovery sample has an unusual situation:
1. Initial BIDSIFY (Mar 14): Successfully processed 3/5 subjects (s03, s10, s19) with full data
2. Directory became read-only for preprocessing handoff
3. S29 and S43 entries were silently dropped due to Flywheel connectivity/API rate limiting during parallel processing
4. Secondary run (Mar 17): Added missing subjects with targeted, serial processing (max_workers=2)

This two-stage approach is acceptable because:
- All files are properly organized in BIDS format
- Reconciliation.json documents complete session information
- Preprocessing tools don't care about completion timestamp
- Data integrity verified through BIDS validator
